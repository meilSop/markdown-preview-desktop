# 结束工作

结束当前会话：归档活跃任务（以及用户想要清理的任何其他已完成但未归档的任务）并记录会话日志。代码提交不在此处进行——那些在工作流第 3.4 阶段调用此命令之前完成。

## 第 1 步：调查当前状态

```bash
python ./.trellis/scripts/get_context.py --mode record
```

这将输出：

- **我的活跃任务** — 审查除了当前任务之外是否有任何实际上已完成（代码已合并，验收标准已满足）并应该在本轮归档的任务。
- **Git 状态** — 快速查看哪些文件有变更。
- **最近的提交** — 你将在第 4 步中需要它们的哈希值用于 `--commit`。

如果 `--mode record` 显示了与当前会话无关的其他已完成任务，向用户展示并一次性确认："这 N 个任务看起来已完成——在本轮也归档它们吗？[y/N]"。默认为否；当前活跃任务无论如何都会在第 3 步中归档。

## 第 2 步：健全性检查 — 分类脏路径

运行：

```bash
git status --porcelain
```

过滤掉 `.trellis/workspace/` 和 `.trellis/tasks/` 下的路径——这些由 `add_session.py` 管理，`task.py archive` 会自动提交，并且会作为此 skill 自身工作的一部分显示为脏。

对于每个剩余的脏路径，判断它属于**当前任务**还是**其他并行工作**（例如，另一个终端窗口编辑同一个仓库）。启发式规则：

- 在当前任务的 `prd.md` / `implement.jsonl` / `check.jsonl` 中引用的路径 → 当前任务
- 在与任务声明范围匹配的代码区域中的路径，或者你记得在本会话中编辑过的路径 → 当前任务
- 在不相关区域中且你没有任何在本会话中触碰过它们的路径 → 其他并行工作

然后路由：

- **任何剩余路径看起来像是当前任务的工作** — 退出并提示：
  > "工作树有来自此任务的未提交代码变更：`<list>`。返回工作流第 3.4 阶段提交它们，然后再运行 `$finish-work`。"

  不要在此处运行 `git commit`。不要提示用户提交。用户返回第 3.4 阶段，由 AI 在那里驱动批量提交。
- **所有剩余路径看起来不相关**（其他并行窗口的工作）— 报告一次并继续到第 3 步：
  > "提示，此任务范围之外的脏文件——留给另一个窗口处理：`<list>`。"
- **确实不确定** — 询问用户一次："`<list>` 是我忘记提交的此任务的工作，还是另一个窗口的？（commit / ignore）" — 然后按照他们的回答路由。

## 第 3 步：归档任务

```bash
python ./.trellis/scripts/task.py archive <task-name>
```

至少：当前活跃任务（如果有）。加上用户在第 1 步中确认的任何额外任务。每次归档通过脚本的自动提交生成一个 `chore(task): archive ...` 提交。

如果没有活跃任务且用户没有确认任何清理归档，则跳过此步骤。

## 第 4 步：记录会话日志

```bash
python ./.trellis/scripts/add_session.py \
  --title "Session Title" \
  --commit "hash1,hash2" \
  --summary "Brief summary"
```

使用第 3.4 阶段产生的工作提交哈希值（在第 1 步的 `Recent commits` 列表中可见，或通过 `git log --oneline`）用于 `--commit` 参数。不要包含第 3 步中的归档提交哈希值。这会生成一个 `chore: record journal` 提交。

最终 git log 顺序：`<来自 3.4 的工作提交>` → `chore(task): archive ...`（一个或多个）→ `chore: record journal`。
