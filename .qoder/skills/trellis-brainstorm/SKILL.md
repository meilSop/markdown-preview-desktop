# Trellis Brainstorm

## 不可协商的规划契约

构建、实现、修复、重构或"继续"的请求，不代表批准离开规划阶段。任务创建许可同样不是实现批准。

对于每个非简单任务，用户必须在初始请求之后至少回复一次，才能开始实现。如果无需澄清，该回复必须批准下述最终规划摘要。

当任何用户侧的产品、范围、UX、兼容性、风险或验收决策尚未解决时，以一个最高价值问题结束当前轮次。不要编辑产品代码、派遣实现、或运行 `task.py start`。

## 不可协商的证据规则

如果一个问题可以通过探索代码库来回答，那就探索代码库来回答。

这是强制性的。在向用户提问之前，先检查答案是否已经可以从代码、测试、配置、文档、现有规范或任务历史中获得。

不要要求用户确认代码库可以回答的事实。只在产品意图、偏好、范围、风险容忍度、验收行为、或检查后仍然模糊的决策方面向用户提问。

代码库证据可以确定当前行为和技术约束。用户的预期行为、功能范围边界和 UX 偏好永远不能仅凭代码库证据回答，即使存在现有模式也是如此；现有模式是选项和推荐证据，而非决策。

---

在阶段一（Phase 1）规划期间使用此技能，将用户的请求转化为清晰的需求和规划产物。

## 前置条件

仅在已获得任务创建许可且用户准备好进入 Trellis 规划后才使用此技能。

如果尚无任务，先创建一个：

```bash
TASK_DIR=$(python ./.trellis/scripts/task.py create "<short task title>" --slug <slug>)
```

从用户请求中提取简洁的标题。使用不带日期前缀的 slug。`task.py create` 会自动添加 `MM-DD-` 目录前缀。

`task.py create` 会创建默认的 `prd.md`。在提出后续问题之前，先用当前理解更新该文件。

## 规划流程

1. 在 `prd.md` 中捕获用户的请求和初始已知事实。
2. 在提问之前检查可用证据：
   - 代码、测试、fixtures 和配置
   - README 文件、文档、现有规范和领域笔记
   - 相关的 Trellis 任务、研究文件和会话历史（如存在）
3. 将发现的内容分类为：
   - 已确认的事实
   - 仍需用户提供的产品意图
   - 仍需用户做出的范围或风险决策
   - 可能超出范围的项
4. 如果仍有需要用户决定的事项，提出唯一最高价值的问题，包含你的推荐和权衡，然后停止。不要在同一轮次中执行实现工作。
5. 每次用户回答后，更新 `prd.md`，重新计算决策清单，然后从第 2 步重复。
6. 当没有需要用户决定的事项时，为复杂任务创建或更新 `design.md` 和 `implement.md`。
7. 运行需求收敛门控，然后执行 PRD 收敛检查。
8. 展示最终规划摘要并停止。不要在同一轮次中运行 `task.py start` 或编辑产品代码。
9. 只有后续用户消息明确批准最新规划摘要后，才能授权 `task.py start` 和实现。如果产物在批准后发生实质性变化，重复最终审查。

不要发明项目特定的产品/规范层次结构。如果代码库已有产品、领域或规范文档，使用它们。如果没有，则使用现有的证据继续。

## 提问规则

每条消息只提一个问题。

每个问题必须包含：

- 需要的决策
- 答案的重要性
- 你的推荐答案
- 用户选择不同方案时的权衡

不要提出流程性问题，例如是否搜索、检查文件或继续头脑风暴。直接进行证据工作。只有在剩余问题是产品决策、偏好、范围边界或风险容忍度选择时才向用户提问。

推荐不是默认选择。永远不要仅仅因为用户要求实现就代替用户做出推荐的产品决策。

当请求和代码库证据已经解决了所有决策时，不要制造澄清问题。在这种情况下，直接进入最终规划摘要，这仍然需要后续的明确批准。

最终审查是必需的阶段转换门控，不是被禁止的流程问题。任务创建许可、初始实现请求以及在最新最终摘要之前给出的批准都不能满足此门控。

## 思维框架：第一性原理分析

当需求模糊、解决方案感觉过度工程化、或者你即将因为"大家都这样做"而增加复杂性时——先分解到基本事实，再向上推理。

### 步骤 1：重述问题

去掉实现细节，浓缩为一句话。

> 错误："我们需要为用户资料端点添加 Redis 缓存"
> 正确："用户资料数据加载时间过长"

### 步骤 2：列出基本事实

什么是绝对正确的（不是观点或惯例）？

| 类别           | 示例                          |
| -------------- | ----------------------------- |
| **物理约束**   | 网络延迟 ≥ 0，磁盘 I/O 有上限 |
| **业务规则**   | "用户必须看到自己的数据"      |
| **技术不变量** | "数据必须一致"                |
| **用户需求**   | "用户希望在 Y 秒内完成 X"     |

### 步骤 3：挑战假设

对于当前计划的每个组成部分：

- **事实还是惯例？** "我们一直用 REST"——为什么？
- **如果去掉会怎样？** 如果什么都不坏，它就是不必要的。
- **解决的是实际问题还是症状？** 追踪因果链。
- **谁从这种复杂性中受益？** 如果"没有人"，就简化。

### 步骤 4：从事实出发构建

1. 从满足所有事实的最小可行机制开始
2. 只有当特定事实需要时才增加复杂性
3. 每个新增必须回答："哪个事实需要这个？"

### 步骤 5：验证

- 解决方案是否解决了原始问题？
- 哪些假设需要验证？
- 测试它的最简单实验是什么？

## 需求收敛门控

在最终审查之前，验证以下所有条件：

- 用户成果和产品价值是明确的
- 范围内和范围外的行为是明确的
- 验收标准描述了可观察的结果
- 用户侧的产品、范围、UX、兼容性和风险决策已解决
- 阻塞性未解决问题为空
- 技术未知项已研究或明确推迟且不影响 MVP 行为

轻量级任务可以省略 `design.md` 和 `implement.md`；但不能跳过证据检查、需求收敛、最终审查或新的实现批准。

最终规划摘要必须展示目标（Goal）、范围内（In Scope）、范围外（Out of Scope）、验收标准（Acceptance Criteria）、关键决策（Key Decisions）、相关风险或推迟项（Risks or Deferred Items），以及产物状态。

## 产物规则

`prd.md` 记录需求和验收标准：

- 目标和用户价值
- 已确认的事实
- 需求
- 验收标准
- 超出范围
- 仍然阻塞规划的未解决问题

`design.md` 记录复杂任务的技术设计：

- 架构和边界
- 数据流和契约
- 兼容性和迁移说明
- 重要权衡
- 运维或回滚考虑

`implement.md` 记录复杂任务的执行计划：

- 有序的实现检查清单
- 验证命令
- 高风险文件或回滚点
- `task.py start` 之前的后续检查

轻量级任务可能只有 `prd.md`。复杂任务在 `task.py start` 之前必须有 `prd.md`、`design.md` 和 `implement.md`。

`implement.md` 不能替代 `implement.jsonl`。在子代理派遣工作流中，`implement.jsonl` 和 `check.jsonl` 在 `task.py start` 之前必须各包含至少一个真实的规范/研究条目；种子 `_example` 行不计入。内联工作流跳过此 JSONL 门控，因为阶段二通过 `trellis-before-dev` 加载上下文。

## PRD 收敛检查

在宣布规划就绪或运行 `task.py start` 之前，按照上述产物规则中描述的最终结构重写 `prd.md` 一次。这不是可选的清理工作；这是最终的规划门控。

此检查必须是无损的：

- 将重复事实合并到一个权威部分。
- 将临时头脑风暴部分（如 `What I already know`、`Assumptions` 和已解决的 `Open Questions`）合并到目标、背景、需求、技术说明或验收标准中。
- 移除已解决的未解决问题，而不是留下空的或已回答的部分。
- 当并行描述同一工作时，合并缺陷和需求列表；保留每个缺陷的严重程度、证据和 file:line 锚点在所属需求上。
- 保留每个 file:line 锚点、决策、约束、需求 ID 和验收标准映射。
- 当存在任何阻塞性未解决问题时，不要进入最终审查。

检查完成后，从头到尾阅读 `prd.md`，验证没有事实在多个部分重复，除非重复增加了新信息。

## 质量标准

在宣布规划就绪之前：

- `prd.md` 包含可测试的验收标准。
- `prd.md` 已通过 PRD 收敛检查：无未解决的临时头脑风暴部分、无跨部分重复事实、无丢失的锚点、决策或验收映射。
- 代码库可回答的问题已通过检查回答。
- 阻塞性未解决问题为空。
- 复杂任务有 `design.md` 和 `implement.md`。
- 子代理派遣任务在 `implement.jsonl` 和 `check.jsonl` 中有真实的策划条目；仅有种子的清单不就绪。
- 最新最终规划摘要已展示给用户。
- 用户在后续消息中明确批准了该摘要用于实现。

不要仅仅因为用户最初要求实现就开始实现。
