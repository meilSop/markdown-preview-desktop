# 代码质量检查

对最近编写的代码进行全面质量验证。结合规范合规性、跨层安全性和提交前检查。

---

## 步骤 1：识别变更内容

```bash
git diff --name-only HEAD
git status
```

## 步骤 2：阅读任务产物和适用规范

按顺序阅读当前任务产物：

- `prd.md`
- `design.md`（如存在）
- `implement.md`（如存在）

```bash
python ./.trellis/scripts/get_context.py --mode packages
```

对于每个变更的包/层，阅读规范索引并遵循其 **Quality Check** 部分：

```bash
cat .trellis/spec/<package>/<layer>/index.md
```

阅读引用的具体指南文件——索引是指针，不是目标。

## 步骤 3：运行项目检查

运行项目的 lint、类型检查和测试命令。在继续之前修复所有失败。

## 步骤 4：对照检查清单审查

### 代码质量

- [ ] Linter 通过？
- [ ] 类型检查器通过（如适用）？
- [ ] 测试通过？
- [ ] 没有遗留调试日志？
- [ ] 没有抑制的警告或绕过类型安全？

### 测试覆盖

- [ ] 新功能 → 添加了单元测试？
- [ ] Bug 修复 → 添加了回归测试？
- [ ] 行为变更 → 更新了现有测试？

### 规范同步

- [ ] `.trellis/spec/` 是否需要更新？（新模式、约定、经验教训）

> "如果我修复了一个 Bug 或发现了非显而易见的东西，是否应该记录下来以免未来的自己遇到同样的问题？" → 如果是，更新相关规范文档。

### 范围纪律

- [ ] 是否有任务不要求的代码整理？
- [ ] 是否为尚不存在的场景添加了抽象、配置或扩展点？
- [ ] 是否为不可能发生的状态添加了投机性回退？
- [ ] 是否有验收标准未提及的文件被修改？
- [ ] 是否在调用方添加了变通方案，而非在行为实际所在位置修复？

## 步骤 5：跨层维度（如适用）

如果你的变更仅限于单层，跳过此步骤。

### A. 数据流（变更涉及 3+ 层）

- [ ] 读取流追踪正确：Storage → Service → API → UI
- [ ] 写入流追踪正确：UI → API → Service → Storage
- [ ] 类型/模式在层之间正确传递？
- [ ] 错误正确传播到调用方？

### B. 代码复用（修改常量、创建工具函数）

- [ ] 创建新代码之前搜索了已有的类似代码？
  ```bash
  grep -r "pattern" src/
  ```
- [ ] 如果同一个值重复出现，它是否代表一个稳定的概念，其调用方必须一起变更？只有在这种情况下才提取——两个仅仅是当前恰好相同的字面量应该保持独立。
- [ ] 批量修改后，所有出现的地方都已更新？

### C. 导入/依赖（创建新文件）

- [ ] 导入路径正确（相对 vs 绝对）？
- [ ] 没有循环依赖？

### D. 同层一致性

- [ ] 使用相同概念的其他地方是否一致？

---

## 步骤 6：报告并修复

报告你发现的每个违规。然后：

- 机械性和局部性问题（lint 小问题、缺少类型、错误导入、死分支、失败的断言）→ 就地修复，然后重新运行项目检查。
- 设计或判断性问题（命名共享概念、移动模块边界、更改公共接口、重新分配行为所在位置）→ 记录证据和你的建议，然后停止。不要静默重写。

如果修复会触及当前任务范围之外的文件，说明情况并停止，而不是扩大变更范围。
