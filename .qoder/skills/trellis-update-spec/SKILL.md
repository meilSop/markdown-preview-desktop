# 更新代码规范 - 沉淀可执行契约

当你学到有价值的东西（从调试、实现或讨论中），使用此技能更新相关代码规范文档。

**时机**：完成任务、修复 Bug 或发现新模式之后

---

## 代码规范优先规则（关键）

在此项目中，实现工作的"规范"是指**代码规范**：
- 可执行契约（非纯原则性文本）
- 具体的签名、载荷字段、环境键和边界行为
- 可测试的验证/错误行为

如果变更涉及基础设施或跨层契约，代码规范深度是强制性的。

### 强制触发条件

当变更包含以下任何一项时，应用代码规范深度：
- 新增/变更的命令或 API 签名
- 跨层请求/响应契约变更
- 数据库 schema/迁移变更
- 基础设施集成（存储、队列、缓存、密钥、环境配置）

### 强制输出（7 个部分）

对于触发的任务，包含以下所有部分：
1. 范围 / 触发条件
2. 签名（命令/API/DB）
3. 契约（请求/响应/环境）
4. 验证与错误矩阵
5. 好/基准/坏用例
6. 所需测试（含断言点）
7. 错误 vs 正确（至少一对）

## 何时更新代码规范

| 触发条件           | 示例                      | 目标规范                        |
| ------------------ | ------------------------- | ------------------------------- |
| **实现了功能**     | 添加了新集成或模块        | 相关规范文件                    |
| **做出了设计决策** | 选择了可扩展性而非简单性  | 相关规范 + "设计决策"部分       |
| **修复了 Bug**     | 发现了错误处理的微妙问题  | 相关规范（如错误处理文档）      |
| **发现了模式**     | 找到了更好的代码组织方式  | 相关规范文件                    |
| **遇到了陷阱**     | 发现 X 必须在 Y 之前完成  | 相关规范 + "常见错误"部分       |
| **建立了约定**     | 团队就命名模式达成一致    | 质量指南                        |
| **新的思维触发器** | "在做 Y 之前别忘了检查 X" | `guides/*.md`（作为检查清单项） |

**关键洞察**：代码规范更新不仅仅是为了问题。每个功能实现都包含未来 AI/开发者需要安全执行的设计决策和契约。

## 规范结构概览

```
.trellis/spec/
├── <layer>/           # 每层编码标准（如 backend/, frontend/, api/）
│   ├── index.md       # 概览和链接
│   └── *.md           # 主题特定指南
└── guides/            # 思维检查清单（不是编码规范！）
    ├── index.md       # 指南索引
    └── *.md           # 主题特定指南
```

### 关键：代码规范 vs 指南 - 了解区别

| 类型         | 位置           | 目的                   | 内容风格                       |
| ------------ | -------------- | ---------------------- | ------------------------------ |
| **代码规范** | `<layer>/*.md` | 告诉 AI "如何安全实现" | 签名、契约、矩阵、用例、测试点 |
| **指南**     | `guides/*.md`  | 帮助 AI "思考什么"     | 检查清单、问题、指向规范的指针 |

**决策规则**：问自己：

- "这是**如何编写**代码" → 放在规范层目录
- "这是编写前**要考虑什么**" → 放在 `guides/`

**示例**：

| 学到的内容                  | 错误位置                            | 正确位置                    |
| --------------------------- | ----------------------------------- | --------------------------- |
| "此任务用 API X 而非 API Y" | ❌ `guides/`（对思维指南来说太具体） | ✅ 相关规范文件（具体约定）  |
| "做 Y 时记得检查 X"         | ❌ 规范文件（对规范来说太抽象）      | ✅ `guides/`（思维检查清单） |

**指南应该是简短的检查清单并指向规范**，而非重复详细规则。

## 更新流程

### 步骤 1：识别你学到了什么

回答以下问题：

1. **你学到了什么？**（具体说明）
2. **为什么重要？**（它能防止什么问题？）
3. **它属于哪里？**（哪个规范文件？）

### 步骤 2：分类更新类型

| 类型         | 描述                    | 操作                       |
| ------------ | ----------------------- | -------------------------- |
| **设计决策** | 为什么选择方案 X 而非 Y | 添加到"设计决策"部分       |
| **项目约定** | 在此项目中我们如何做 X  | 添加到相关部分并附示例     |
| **新模式**   | 发现的可复用方法        | 添加到"模式"部分           |
| **禁止模式** | 会导致问题的做法        | 添加到"反模式"或"不要"部分 |
| **常见错误** | 容易犯的错误            | 添加到"常见错误"部分       |
| **约定**     | 商定的标准              | 添加到相关部分             |
| **陷阱**     | 非显而易见的行为        | 添加警告提示               |

### 步骤 3：阅读目标代码规范

编辑前，阅读当前代码规范以：
- 理解现有结构
- 避免重复内容
- 为你的更新找到合适的部分

```bash
cat .trellis/spec/<category>/<file>.md
```

### 步骤 4：进行更新

遵循以下原则：

1. **具体**：包含具体示例，而非仅抽象规则
2. **解释原因**：说明它能防止什么问题
3. **展示契约**：添加签名、载荷字段和错误行为
4. **展示代码**：为关键模式添加代码片段
5. **保持简洁**：每部分一个概念

### 步骤 5：更新索引（如需要）

如果你添加了新部分或代码规范状态变更，更新类别的 `index.md`。

## 更新模板

### 基础设施/跨层工作的强制模板

```markdown
## 场景：<名称>

### 1. 范围 / 触发条件
- 触发条件：<为什么这需要代码规范深度>

### 2. 签名
- 后端命令/API/DB 签名

### 3. 契约
- 请求字段（名称、类型、约束）
- 响应字段（名称、类型、约束）
- 环境键（必需/可选）

### 4. 验证与错误矩阵
- <条件> -> <错误>

### 5. 好/基准/坏用例
- 好：...
- 基准：...
- 坏：...

### 6. 所需测试
- 单元/集成/端到端测试及断言点

### 7. 错误 vs 正确
#### 错误
...
#### 正确
...
```

### 添加设计决策

```markdown
### 设计决策：[决策名称]

**背景**：我们在解决什么问题？

**考虑的方案**：
1. 方案 A - 简要描述
2. 方案 B - 简要描述

**决策**：我们选择了方案 X，因为...

**示例**：
\`\`\`typescript
// 如何实现
代码示例
\`\`\`

**可扩展性**：未来如何扩展...
```

### 添加项目约定

```markdown
### 约定：[约定名称]

**内容**：约定的简要描述。

**原因**：为什么在此项目中我们这样做。

**示例**：
\`\`\`typescript
// 如何遵循此约定
代码示例
\`\`\`

**相关**：相关约定或规范的链接。
```

### 添加新模式

```markdown
### 模式名称

**问题**：这解决什么问题？

**解决方案**：方法的简要描述。

**示例**：
\`\`\`
// 好
代码示例

// 坏
代码示例
\`\`\`

**原因**：解释为什么这样更好。
```

### 添加禁止模式

```markdown
### 不要：模式名称

**问题**：
\`\`\`
// 不要这样做
坏的代码示例
\`\`\`

**为什么不好**：问题说明。

**替代方案**：
\`\`\`
// 改为这样做
好的代码示例
\`\`\`
```

### 添加常见错误

```markdown
### 常见错误：描述

**症状**：出了什么问题

**原因**：为什么会发生

**修复**：如何纠正

**预防**：未来如何避免
```

### 添加陷阱

```markdown
> **警告**：非显而易见行为的简要描述。
>
> 何时发生以及如何处理的详细信息。
```

## 交互模式

如果你不确定要更新什么，回答以下提示：

1. **你刚完成了什么？**
   - [ ] 修复了 Bug
   - [ ] 实现了功能
   - [ ] 重构了代码
   - [ ] 讨论了方案

2. **你学到了什么或决定了什么？**
   - 设计决策（为什么选 X 而非 Y）
   - 项目约定（我们如何做 X）
   - 非显而易见的行为（陷阱）
   - 更好的方法（模式）

3. **未来的 AI/开发者需要知道这个吗？**
   - 理解代码如何工作 → 是，更新规范
   - 维护或扩展功能 → 是，更新规范
   - 避免重复犯错 → 是，更新规范
   - 纯粹的一次性实现细节 → 可能跳过

4. **它涉及哪个领域？**
   - [ ] 后端代码
   - [ ] 前端代码
   - [ ] 跨层数据流
   - [ ] 代码组织/复用
   - [ ] 质量/测试

## 质量检查清单

在完成代码规范更新之前：

- [ ] 内容是否具体且可操作？
- [ ] 是否包含了代码示例？
- [ ] 是否解释了为什么（WHY），而非仅仅是什么（WHAT）？
- [ ] 是否包含了可执行的签名/契约？
- [ ] 是否包含了验证和错误矩阵？
- [ ] 是否包含了好/基准/坏用例？
- [ ] 是否包含了所需测试及断言点？
- [ ] 是否在正确的代码规范文件中？
- [ ] 是否与现有内容重复？
- [ ] 新团队成员能理解吗？

## 与其他命令的关系

```
开发流程：
  学到东西 → $update-spec → 知识已沉淀
       ↑                          ↓
  $break-loop ←────────────── 未来会话受益
  （深度 Bug 分析）
```

- `$break-loop` - 深度分析 Bug，通常揭示需要更新的规范
- `$update-spec` - 实际进行更新
- `$finish-work` - 提醒你检查规范是否需要更新

## 核心理念

> **代码规范是活文档。每次调试会话、每个"顿悟时刻"都是让实现契约更清晰的机会。**

目标是**组织记忆**：
- 一个人学到的东西，所有人受益
- AI 在一个会话中学到的，持久化到未来会话
- 错误变成有文档的防护栏
