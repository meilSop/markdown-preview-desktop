# 思维指南

> **目的**：拓展你的思维，帮你考虑到可能遗漏的地方。

---

## 为什么需要思维指南？

**大多数 bug 和技术债务来源于"没想到"**，而非能力不足：

- 没想到层级边界会发生什么 → 跨层 bug
- 没想到代码模式在重复 → 到处是重复代码
- 没想到边界情况 → 运行时错误
- 没想到未来的维护者 → 代码难以阅读

这些指南帮助你在**编码之前提出正确的问题**。

## 快速参考：思维触发点

### 何时需要考虑跨层问题

- [ ] 功能涉及 3 个及以上层级（API、Service、Component、Database）
- [ ] 数据格式在层级之间发生变化
- [ ] 多个消费方需要相同的数据
- [ ] 你不确定某些逻辑应该放在哪里
- [ ] 你正在添加事件类型、JSONL 记录、RPC 载荷或配置字段
- [ ] UI / 命令代码开始直接转换原始载荷字段

→ 阅读 [跨层思维指南](./cross-layer-thinking-guide.md)

### 何时需要考虑代码复用

- [ ] 你正在编写与已有代码类似的代码
- [ ] 你看到同一模式重复出现 3 次及以上
- [ ] 你正在向多个位置添加新字段
- [ ] **你正在修改任何常量或配置**
- [ ] **你正在创建新的工具函数/辅助函数** ← 先搜索！
- [ ] 两个文件用本地类型转换读取相同的无类型载荷字段
- [ ] 多个分支基于 `kind` / `action` 更新相同的派生状态

→ 阅读 [代码复用思维指南](./code-reuse-thinking-guide.md)

### 验证 AI 交叉审查结果时

- [ ] 审查者声称"用户输入可能是恶意的" → 检查实际数据来源（内部清单？用户配置？外部 API？）
- [ ] 审查者标记"缺少验证" → 数据是否来自可信的内部来源？
- [ ] 审查者说"行为变更" → 阅读代码注释 — 这是有意的设计吗？
- [ ] 审查者在测试中发现"bug" → 假设被测试的功能不存在 — 测试还能通过吗？如果能 → 同义反复测试

**常见的 AI 审查者误报模式**：
1. **信任边界混淆**：将内部数据（打包的 JSON 清单）视为不可信的外部输入
2. **忽略设计注释**：将代码注释中记录的有意行为标记为 bug
3. **变量误读**：未追踪变量到其实际定义（例如，按路径 vs 按名称作为 key 的 Map）

**验证规则**：每个 CRITICAL/WARNING 级别的发现在排定优先级之前必须对照实际代码进行验证。AI 审查的误报率约为 35%。

## 修改前规则（关键）

> **在修改任何值之前，务必先搜索！**

```bash
# Search for the value you're about to change
grep -r "value_to_change" .
```

这一个习惯就能防止大多数"忘记更新 X"的 bug。

## 如何使用本目录

1. **编码前**：浏览相关的思维指南
2. **编码中**：如果某些东西感觉重复或复杂，查看指南
3. **出 bug 后**：将新的经验教训添加到相关指南中（从错误中学习）
